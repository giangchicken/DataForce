# Guided Validation — LLM-Generated Questions for Dataset Review

## What

Guided validation is a task presentation mode in DataForce where an annotator, instead of facing a raw labeling form, is shown **one LLM-generated question at a time** about a single dataset record — *"Case này gọi tool `VerifyEmail_15d` có đúng không?"* — together with the evidence the question refers to and a glossary of the domain notation needed to answer it. The annotator answers correct / incorrect / unsure, and when they answer incorrect they must supply the corrected value. Questions are generated in batch before tasks reach the queue and cached on the task. The first target is the Tool-Decision function-calling dataset; the mechanism is generic and driven by a per-project question-generation profile.

## Context

This mode exists because the dataset it targets cannot be validated with a plain form. A record in `Tool-Decision-Model/dataset/fc_train_final.json` looks like this:

```json
{
  "idx": 0,
  "messages": [
    { "role": "system",    "content": "Based on the available tools ... TOOLS:\n[VerifyEmail_15d]\nMục đích: ...\nKhi nào gọi: {trigger} khách hàng cung cấp email ...\nKhi nào KHÔNG gọi: {hold_other} khách hàng chỉ cung cấp số điện thoại {or} ...\nrequire: email\nparams:\n  email* (string): ... {constraint} đúng định dạng email ..." },
    { "role": "user",      "content": "A: Dạ em chào anh chị ...\nU: email của anh là <ĐỊA CHỈ EMAIL ĐỌC DẠNG NÓI>" },
    { "role": "assistant", "content": "[\"VerifyEmail_15d\"]" }
  ],
  "meta": { "label": ["VerifyEmail_15d"], "llm_model": "gemma-4-31B-it", "source_index": 0 }
}
```

Measured across the file: **21,172 records**, and the label is not a simple yes/no.

| Tools called | Records | Share |
|---|---:|---:|
| 0 (call nothing) | 7,486 | 35.4% |
| 1 | 10,608 | 50.1% |
| 2 | 2,757 | 13.0% |
| 3 | 321 | 1.5% |

The single-tool majority is the easy case. The 35% zero-label population is where the dataset's quality actually lives — those are the records asserting *no tool should fire*, and judging them requires reading the "Khi nào KHÔNG gọi" clauses.

Those clauses are written in a marker DSL. Scanning the whole file gives its exact vocabulary and weight:

| Marker | Occurrences |
|---|---:|
| `{or}` | 262,242 |
| `{hold_other}` | 155,150 |
| `{hold_missing}` | 110,210 |
| `{trigger}` | 103,969 |
| `{constraint}` | 51,131 |
| `{and}` | 45,982 |
| `{force}` | 8,314 |
| `{after}` | 1,400 |
| `{turn_trigger}` | 881 |
| `{before}` | 261 |

An annotator who does not know that `{hold_missing}` means *withhold the call because a required input has not been supplied yet* cannot distinguish a correct zero-label from a mislabeled one. That glossary is not decoration — it is the thing that makes the task answerable, and it is why the platform's generic labeling UI is insufficient here.

`meta` is heterogeneous across the file — `label` is the only key present in every record; `llm_model`, `source_index`, `domain`, `scenario`, `source`, and `gen_category` appear in varying combinations, with five distinct shapes covering the bulk. The adapter must tolerate that rather than assume one schema.

This spec depends on [`docs/dataforce-platform/spec.md`](../dataforce-platform/spec.md) for tasks, reservations, review, and export, and on [`docs/agent-toolkit/spec.md`](../agent-toolkit/spec.md) for the LLM client, `slot_filling`, `extract_json_from_text`, and the streaming JSON reader that makes a 127MB import possible.

## Requirements

### Import

1. A `fc_tool_decision` dataset adapter maps each array element to one DataForce task: `external_id` from `idx`, the tool catalog parsed out of the system message, the conversation from the user message, and the current label from `meta.label`.
2. Import streams the file via `agent_toolkit.file_utils.iter_json_array_file`. Importing the 127MB, 21,172-record file must not load it whole.
3. The adapter parses the system message's `TOOLS:` block into a structured catalog — per tool: name, purpose, call conditions, hold conditions, required params, and each param's type, requiredness, and constraints — preserving the marker tokens verbatim.
4. Records whose system message fails to parse are imported with `parse_status = "unparsed"`, retaining the raw text, and are excluded from question generation until a manager acts. Import never silently drops a record, and the import summary reports the unparsed count.
5. `meta` is stored whole. The adapter requires only `label`; every other key is carried through untouched.

### Question generation

6. Questions are generated by a batch job before tasks enter any queue, never on the annotator's request path.
7. A generation profile is project-level configuration: the target LLM, the prompt template, the marker glossary, the enabled question focuses, and the per-run token budget.
8. Each generated question carries: the question text, a focus, the evidence it refers to (the specific conversation turn and tool under discussion), the glossary entries relevant to that record, the answer options, and the generator's model and prompt version.
9. Question focuses for this dataset: `tool_selection` (is the called set right), `no_call_justified` (for zero-label records, was withholding correct), `missing_call` (was a tool omitted), and `param_constraint` (does the extracted argument satisfy its `{constraint}`).
10. The generator's own proposed answer is stored on the question but **not shown to the annotator**.
11. A generation run reports estimated token cost before it starts and refuses to exceed the profile's budget, stopping cleanly with a partial result rather than overrunning.
12. Generation is idempotent per `(task, prompt_version, model)`: re-running skips tasks that already have a current question. Regeneration is an explicit manager action.

### Answering

13. The annotator sees exactly one question at a time. Answering advances to the next; there is no form with multiple questions on it.
14. Every question is displayed with its evidence and its glossary entries. The glossary is also available in full at any time.
15. Answer options are `correct`, `incorrect`, and `unsure`. `unsure` requires a free-text reason.
16. Answering `incorrect` requires a correction before the answer can be submitted. For `tool_selection`, `no_call_justified`, and `missing_call`, the correction is a multi-select over that record's own tool catalog plus an explicit "no tool" choice — so the corrected value is always a well-formed label array. For `param_constraint`, it is the corrected argument value.
17. The annotator may optionally attribute the error to a specific clause of a specific tool description, choosing the tool and the clause type (`trigger`, `hold_other`, `hold_missing`, `constraint`, `other`).
18. The annotator may flag a question as unusable — `not_answerable`, `wrong_evidence`, `nonsensical`, or `duplicate` — which ends the task without producing an answer, marks the question dead, and queues the task for regeneration.
19. A record whose question was flagged never counts as validated.

### Quality and output

20. Guided-validation answers are annotations under the platform's model and inherit overlap, reservation, review, and agreement unchanged.
21. Where a correction exists and has been accepted, export emits the corrected label; otherwise the original. Every exported record states which it is.
22. Export for this dataset round-trips the source format: the same `{idx, messages, meta}` shape, with `meta.label` replaced by the accepted value and `meta.dataforce` recording the provenance — validator, verdict, whether corrected, and the source dataset version.
23. Agreement between the withheld generator answer and the accepted human answer is tracked per project and per question focus.

## Design

### Import pipeline

```
fc_train_final.json  (127MB, 21,172 records)
        │  iter_json_array_file  — bounded memory
        ▼
  fc_tool_decision adapter
        │  ├─ parse TOOLS: block → tool catalog (markers preserved)
        │  ├─ split conversation on ^A:/^U: line prefixes
        │  └─ meta passthrough, label extracted
        ▼
  task.data = { conversation, tool_catalog, current_label, raw_system, meta }
  task.meta = { parse_status, source_idx, marker_counts }
```

The `TOOLS:` block is parsed by section, not by one regex over the whole thing: split on `^\[(\w+)\]$` for tool boundaries, then per tool read the labeled lines (`Mục đích:`, `Khi nào gọi:`, `Khi nào KHÔNG gọi:`, `require:`, `params:`) and the indented param lines under `params:`. Marker tokens are left in the extracted strings verbatim — they are content the annotator must see, not syntax to strip. A tool block missing `Mục đích:` or `params:` marks the whole record `unparsed`.

### Question generation job

A Celery job over tasks lacking a current question:

```
for each batch of tasks:
    prompt = slot_filling(profile.template, {
        tool_catalog, conversation, current_label, glossary, focus
    })
    raw    = await agent_toolkit.llm.complete(prompt, model=profile.model, ...)
    q      = extract_json_from_text(raw)
    validate against QuestionSchema → persist, or mark generation_failed
```

Concurrency and rate limiting come from the toolkit's `TrafficController`, configured from the profile. The job accumulates token usage and halts at the budget, leaving already-generated questions in place.

Focus selection is deterministic, from the record rather than the LLM: zero-label records get `no_call_justified`; records with a label get `tool_selection`; records whose called tools declare `{constraint}` params get an additional `param_constraint` question. A record therefore yields one or two questions, and each question is its own task in the queue — which is what "one question at a time" means at the data layer, not just the UI layer.

### Stored question

```json
{
  "id": "01JQ...",
  "task_id": "01JR...",
  "focus": "no_call_justified",
  "question": "Trong tình huống này, trợ lý KHÔNG gọi tool nào. Quyết định đó có đúng không?",
  "evidence": {
    "turn": "U: cho anh hỏi thời tiết thế nào",
    "tools_in_scope": ["GetTemperature_020"],
    "clause": "Khi nào KHÔNG gọi: ... {hold_missing} khách chưa cung cấp tên địa điểm cụ thể."
  },
  "glossary": ["hold_missing", "trigger"],
  "options": ["correct", "incorrect", "unsure"],
  "generator": { "model": "GLM-5.1", "prompt_version": 3,
                 "proposed_answer": "correct", "confidence": 0.86 },
  "status": "active"
}
```

`generator.proposed_answer` is never serialized into the annotator-facing payload. That exclusion is enforced at the response schema, not by UI omission, and is covered by a contract test.

### Marker glossary

Project-level configuration, versioned with the generation profile, rendered beside every question and expandable in full. The starting content, with the semantics inferred from usage across the corpus:

| Marker | Gloss (vi) | Meaning |
|---|---|---|
| `{trigger}` | Điều kiện kích hoạt | A condition that should cause the tool to be called |
| `{or}` | Hoặc | Alternatives — any one adjacent condition suffices |
| `{and}` | Và | Conjunction — all adjacent conditions must hold |
| `{hold_other}` | Không gọi — đã có hướng khác | Withhold: another tool or path covers this |
| `{hold_missing}` | Không gọi — thiếu thông tin | Withhold: a required input has not been supplied yet |
| `{constraint}` | Ràng buộc tham số | A format or value restriction on a parameter |
| `{force}` | Bắt buộc gọi | Call unconditionally when the condition holds |
| `{after}` / `{before}` | Sau / Trước | Ordering relative to another tool |
| `{turn_trigger}` | Kích hoạt trong lượt | Trigger scoped to the current dialogue turn |

**These glosses are inferred from reading the corpus, not from a specification, and they must be confirmed before any annotation runs.** Every judgment in this project is made against them; if `{hold_other}` means something else to whoever authored the tool descriptions, 155,150 occurrences of it get validated against the wrong rule and the resulting corrections are worse than no corrections. Treat confirming this table as a blocking prerequisite, not a detail.

### Answer

```json
{
  "answer": "incorrect",
  "correction": { "label": ["GetTemperature_020"] },
  "error_attribution": { "tool": "GetTemperature_020", "clause": "hold_missing" },
  "note": "Khách đã nói 'ở Hà Nội' ở lượt trước nên không thiếu địa điểm.",
  "lead_time_ms": 18400
}
```

Stored as the platform's `annotation.result`, so overlap, agreement, review, and audit apply with no special-casing.

### UI

A single centered card: the question, the evidence with the referenced turn highlighted, the relevant glossary entries inline, and three answer buttons with number hotkeys. Choosing `incorrect` expands the correction control — the record's own tool catalog as a multi-select plus an explicit "Không gọi tool nào" option, so a correction is always a valid label array and never free text. A persistent secondary action flags the question as unusable. Submitting loads the next question; nothing else is on screen.

The full conversation and complete tool catalog are collapsed by default and one click away. The default view is deliberately narrow — the whole point of one question at a time is that the annotator judges one thing.

### Schema additions

```
question_profile(id, project_id→, model, prompt_version, template,
                 glossary JSONB, enabled_focuses TEXT[], token_budget, created_at)
validation_question(id, task_id→, profile_id→, focus, question, evidence JSONB,
                    glossary_keys TEXT[], generator JSONB, status, created_at,
                    UNIQUE(task_id, focus, profile_id))
generation_run(id, project_id→, profile_id→, requested, generated, failed,
               tokens_used, estimated_cost, status, error, started_at, finished_at)
```

`validation_question.status ∈ {active, superseded, flagged, generation_failed}`.

### Endpoints

```
POST   /api/v1/projects/{id}/question-profile
POST   /api/v1/projects/{id}/generate-questions      → generation_run (async)
GET    /api/v1/generation-runs/{id}
POST   /api/v1/projects/{id}/next-question           reserve + serve one question
POST   /api/v1/questions/{id}/answer
POST   /api/v1/questions/{id}/flag
POST   /api/v1/tasks/{id}/regenerate-question        manager only
```

`next-question` is `next-task` with the question joined in and the generator's answer stripped; it reuses the same reservation transaction rather than introducing a second distribution path.

## Decisions

**Batch pre-generation, cached on the task.** *Alternatives:* generate at serve time; hybrid with synchronous fallback. *Why:* an LLM call in the labeling hot path adds seconds per task to a workflow whose entire value is throughput, and makes cost scale with views rather than records — a re-opened task would pay twice. Batch generation also makes questions inspectable before annotators see them, which matters because a bad question wastes annotator time in a way a bad form does not. *Reversible:* yes, additive — the hybrid fallback can be added later if queue starvation ever shows up in practice.

**The generator's answer is withheld from the annotator.** *Alternatives:* show it as a suggestion, the way pre-annotation normally works. *Why:* the point of this exercise is to catch cases where an LLM's judgment about tool-calling was wrong, and the labels being checked were themselves largely machine-produced — 14,241 of 21,172 records name `gemma-4-31B-it` as their source. Showing an LLM's opinion while asking a human to check an LLM's output invites the annotator to ratify it. Withholding it costs some speed and buys an independent signal — and LLM-vs-human disagreement becomes a usable pointer to hard records. *Reversible:* yes, it is a display flag; but data collected with it on and off are not comparable, so switching mid-project poisons the metric.

**Correction is a multi-select over the record's own tool catalog, never free text.** *Alternatives:* free-text correction. *Why:* the corrected value has to be a valid label array to be usable as a training target. Constraining the input at the UI makes every correction directly exportable and removes a normalization pass that would otherwise have to guess at typos and Vietnamese tool-name variants. *Reversible:* no, in effect — free-text corrections collected early could not be cleanly recovered.

**Focus is chosen by rule, not by the LLM.** *Alternatives:* let the generator decide what to ask. *Why:* the record's label cardinality already determines what the interesting question is — a zero-label record raises "was withholding right", a labeled one raises "is this the right tool". Deciding in code makes coverage predictable and auditable, and stops the generator from asking 21,172 variations of the same easy question. *Reversible:* yes.

**Flagging is a first-class outcome, not a comment.** *Alternatives:* let annotators skip, or leave a note. *Why:* these questions are machine-written and some fraction will be unanswerable. Without a structured flag, bad questions get answered anyway — annotators guess rather than stall — and the noise is invisible in the output. The flag rate is also the only direct measure of generation quality. *Reversible:* no reason to.

**One question per task row, not several per record.** *Alternatives:* one task per record carrying its questions. *Why:* it makes "one question at a time" true in the data model, so overlap, reservation, and agreement all operate at the granularity the annotator actually works at. Two annotators can hold different questions about the same record without contending. *Reversible:* no — it is the primary key of the whole flow.

**Assumption:** the marker glosses above are correct. Blocking, as stated in Design.

**Assumption:** annotators read Vietnamese. Questions, glossary, and UI copy are Vietnamese; the platform chrome stays English in v1.

**Assumption:** `fc_train_final.json` is a snapshot to validate, not a live file. Import records a source checksum; re-importing a changed file creates a new dataset version rather than mutating tasks in place.

## Invariants

1. **The generator's answer never reaches the client.** *Check:* a contract test asserting `proposed_answer` and `confidence` are absent from every `next-question` and `GET question` response body.
2. **No annotator waits on an LLM.** No request path that serves a question calls the LLM client. *Check:* a test that serves questions with the LLM client patched to raise, asserting success.
3. **Corrections are well-formed.** Every stored `correction.label` is a subset of that record's own tool catalog, or empty. *Check:* a DB constraint trigger plus a validation test with an out-of-catalog tool name.
4. **`incorrect` implies a correction.** No answer of `incorrect` exists without one. *Check:* a `CHECK` constraint and an API test.
5. **Flagged questions never validate a record.** *Check:* an export test asserting flagged tasks are absent from output.
6. **Import loses nothing.** Exported record count equals imported record count, and every source `idx` appears exactly once. *Check:* a round-trip test over a 500-record fixture comparing `idx` sets.
7. **Budget is a ceiling.** A generation run's `tokens_used` never exceeds `profile.token_budget`. *Check:* a run against a stub LLM with a tiny budget, asserting a clean partial stop.

## Error Behavior

Inherits the platform's RFC 9457 shape. Specific to this mode:

| Situation | Status | `code` | Behavior |
|---|---|---|---|
| Generation LLM fails after retries | — | — | Task marked `generation_failed` with the error preserved; the run continues. Never serve a task without a question. |
| Generated output fails `QuestionSchema` | — | — | Retried once at temperature 0, then `generation_failed`. Malformed questions are never shown. |
| Budget exhausted mid-run | 200 | — | Run ends `partial` with counts; generated questions are kept. Not an error. |
| `incorrect` submitted with no correction | 422 | `correction_required` | |
| Correction names a tool outside the catalog | 422 | `correction_out_of_catalog` | `errors[]` lists the valid tool names. |
| Answering a flagged or superseded question | 409 | `question_not_active` | Client discards and requests the next. |
| Record unparsed at import | — | — | Imported with `parse_status="unparsed"`, excluded from generation, counted in the import summary. |

The failure that matters most is a *plausible but wrong* question — one that reads fine and asks about the wrong turn. Nothing detects that automatically. The flag rate is the instrument: a project-level flag rate above 10% halts further generation and raises an alert on the profile, on the assumption that the prompt or glossary is wrong rather than the annotators.

## Testing Strategy

- **Adapter:** parse fixtures covering all five observed `meta` shapes, each label cardinality (0, 1, 2, 3), and malformed `TOOLS:` blocks. Assert marker tokens survive parsing verbatim — a test that strips them would pass while destroying the annotator's only evidence.
- **Streaming import:** the full 127MB file in CI-adjacent form (a generated fixture of equal shape), asserting all 21,172 records import, bounded memory, and idempotence on re-import.
- **Focus selection:** the rule mapping over each cardinality, including that a zero-label record yields `no_call_justified` and never `tool_selection`.
- **Generation:** stubbed LLM returning valid JSON, fenced JSON, prose-wrapped JSON, and garbage — asserting `extract_json_from_text` recovers the first three and the fourth marks `generation_failed`. Budget enforcement with a fake tokenizer. Idempotence across two runs at the same prompt version.
- **Answer flow:** the correction requirement, catalog-subset enforcement, flagging ending the task without an annotation, and regeneration superseding rather than deleting.
- **Leak test:** the invariant-1 contract test.
- **Export round-trip:** import a 500-record fixture, answer a known mix of correct/incorrect/flagged, export, and assert the source shape is reproduced with corrected labels substituted and provenance recorded.
- **E2E (Playwright):** import the fixture, generate questions, answer three as two annotators at overlap 2, flag one, have a reviewer resolve a conflict, export, and diff against the expected artifact.
- **Human pilot before scale.** Before generating across 21,172 records, generate 200, have two annotators answer them, and inspect flag rate, agreement, and generator-vs-human disagreement. The prompt and glossary get one revision pass from that pilot. Generating 21k questions against an unvalidated prompt is the most expensive mistake available here, and it is entirely avoidable.

## Out of Scope

- Modalities other than this record shape — image and text projects use the platform's standard labeling UI.
- Adaptive questioning: asking a follow-up based on the previous answer, or ordering by model uncertainty.
- Automatically applying corrections back to the source file. Export produces an artifact; writing it anywhere is a human step.
- Retraining the tool-decision model, or any evaluation loop over corrected data.
- Generating the glossary from the corpus. It is authored and confirmed by a human.
- Multi-language question generation. Vietnamese only.
- Annotator-authored questions.
